# Protected deployment operator, local preparation

Wave 10H adds `scripts/member-hosted/uploader.mjs` as a library. It has no command-line entry point, ambient credentials, default HTTP implementation, automatic request, or authority to deploy. Only synthetic offline tests have invoked it. Existing application source `327ba098628f70aa65140862b8b14cd709bfd711` and all authentication/runtime handlers are unchanged.

## Protected input and trust boundary

`readHiddenCredential({input, output})` requires exclusive, explicitly supplied unencoded TTY streams. It enters raw mode, displays only a fixed prompt, accepts bounded printable ASCII with backspace, rejects escape/control sequences, and restores terminal mode on success, cancellation, error or timeout. It never reads environment variables, command arguments, files, shell history, clipboard or stored credentials. Do not execute it or collect any real values under Wave 10H.

`protectCredential(buffer)` takes ownership, clears the input buffer immediately, and returns an opaque redacted handle. `disposeCredential(handle)` clears its held bytes. The isolated publishable key is disposed after its one finalization attempt or any failure. The provider credential remains inside its transport until `close()`, which the future operator must invoke in its outermost `finally` block, including when preparation fails.

JavaScript and native TLS implementations can create immutable strings or internal copies. Owned buffers are cleared and references are discarded, but physical erasure of every garbage-collected copy cannot be guaranteed. No credential, response body, request body, header, native error, stack cause or wire buffer may be logged, serialized or persisted by injected dependencies. The test HTTP fake deliberately records synthetic input only and must never be reused remotely.

The HTTP implementation, operation-authorization closure, provider reader and package builder are trusted operator code. Dependency injection is not proof of owner authorization. Browser JSON, files supplied by an untrusted caller, an application-generated response, or a Boolean configuration flag cannot provide this authority. There is no bypass of execution-environment approvals.

## Future composition contract, not execution authority

1. Receive a separate exact application-deployment authorization and fresh operator, cost, backend and synthetic-identity evidence before permitting `authorize({phase: 'preflight', ...})`.
2. Explicitly supply reviewed `node:https.request` to `createProtectedApiTransport({credential, requestImpl, authorize})`. Requests are restricted to the fixed Netlify API host and reviewed site/deploy/upload paths. TLS verification stays enabled, redirects are denied, and raw upstream errors are replaced with fixed errors. Both raw and JSON-decoded credential reflection are rejected before successful metadata is projected.
3. Construct `createProviderReceiptReader` with that transport and a separate credential-free immutable-origin HTTP implementation. Never attach the Netlify provider token to the public observer. The public observer must enforce exact immutable origin, allowed paths, no redirects and no credentials for its invalid-body probes.
4. Call `createDeploymentOperator` with the reviewed transport `request`, independent reader, exact-operation `authorize`, clean candidate `preparePackage`, independent `beforeAcceptance`, separately authorized `acceptance`, and **`beginContainment: transport.beginContainment`**. The `preparePackage(pin)` callback must build from clean exact candidate source after receiving the actual provider-reserved ID. It returns only the package directory and independently reviewed expected manifest SHA256. Do not build from the later tooling/documentation HEAD.
5. The operator consumes its single reservation allowance on its first run. Its reservation request contains only draft=true. No substitute or retry is made after ambiguous creation, finalization or upload failure. Deleted Wave 10E/G IDs are denied explicitly. A malformed or rejected reservation cannot authorize deletion: independent complete pre/post inventory must establish that the returned ID is new before it becomes owned cleanup authority.
6. `prepareUpload` invokes the existing independent package verifier with fixtures disabled, validates the exact source/site/project pin, snapshots approved public and native-function bytes and rechecks their hashes. File replacement after this point cannot change the retained upload bytes. It uploads no source tree, local config, manifest, compiled artifact directory, protected resource or evidence file.
7. Same-ID finalization is observed by `createConfigurationReceiptTransport`. Exactly one isolated key is sent in the documented deploy-specific environment field, with functions scope and is_secret=true. The body contains exactly draft/files/functions/functions_config/environment. There is no site/team/context environment API or fallback. The callback must establish protected project provenance before reservation; opaque key syntax alone is insufficient.
8. The operator uses `createArtifactReceiptTransport` around actual byte requests. It retransmits each approved static file and native ZIP exactly once, even if provider digest caching lists fewer required blobs, to obtain complete fresh provider SHA acknowledgments. It rejects extra required digests and refuses incomplete or mismatched acknowledgments. It never retries a blob or uploads an unapproved file. Static SHA1 and ZIP SHA256 are kept distinct.
9. `beforeAcceptance` must return an opaque handle produced by the independent route/rate observer. An arbitrary true value or forged route object is rejected by `composeProviderReceipt`. Required invalid-body route/method/429 evidence precedes any passwords. A declaration of a traffic rule or a successful deployment alone cannot authorize Auth acceptance.
10. The `acceptance` callback receives the composed provider receipt, exact pin and manifest digest. It remains responsible for independently fresh database/key provenance checks and the existing `verifyProviderBinding` contract after separately authorized A/B Auth acceptance. No application echo, successful grant or opaque key syntax supplies missing backend authority. Existing Auth, MFA, CSRF, session, maintenance and RLS policies remain unchanged.
11. Cleanup runs on success or failure, only for the independently established new ID. It rechecks identity/context/unpublished state before cancellation/deletion. It never deletes a historical ID or a currently published deployment. The independent reader requires provider 404s, complete list absence, immutable page/API/direct-function inaccessibility and history/alias preservation. Any uncertain outcome is explicitly unverified containment, not successful cleanup.
12. Close the provider transport in the outermost finally block. Retain only the safe result and independently sanitized receipts. No credential or raw provider response belongs in Git or evidence.

The normal native API transport permits at most 200 requests. A one-way authorized `beginContainment()` transition reserves 40 additional requests for reads and exact cancellation/deletion, never another reservation or finalization. The operator itself caps normal requests and the supervised window separately. The future executable composition must wire this transition; omission can turn quota exhaustion into a containment failure. These limits are guardrails, not automatic deployment expiry, invoice guarantees or a substitute for an available operator.

## Provider evidence limits

The private configuration receipt proves the exact documented deployment-only request and acknowledgment. It does not read back a secret value or independently attest an opaque key's project. Upload acknowledgments establish the actual submitted byte/hash domains; they are not independent downloads of provider-held ZIPs. Complete route/method/denial/rate observations are required before Auth. Backend readiness and authenticated A/B acceptance remain separate, fresh gates. An unpublished deployment is accessible to a holder of its immutable URL and is not an account allowlist or access-private site.

No provider reservation, application upload, credential provisioning, hosted Auth, Supabase request, migration, maintenance change, production action, push or merge is authorized by this preparation.
