# Proposed authenticated contracts and schema changes

Everything in this file is **PROPOSED**, not implemented/approved/applied. Names below are design placeholders to be reconciled by the migration owner. No SQL or migration file is created. Keep all existing280 bytes unchanged; allocate any future migration only after central review, never assume281 is available.

## HTTP and identity contract

Keep current same-origin BFF routes. Define a separate `AuthenticatedMemberIdentity` union: unknown/loading/unavailable; or authenticated `{subjectId, sessionBoundary, environment:'isolated', assurance:'aal1'|'aal2', permissions}`. All trusted fields come from server-validated current Auth session plus authoritative permission reads. Browser cannot submit/override subjectId, organization, grants, AAL, inviter, leader, session active or privilege. `sessionBoundary` is opaque per-user/session/generation and carries no bearer token or raw session ID. Current synthetic props remain unchanged.

Responses are allowlisted versioned JSON, private/no-store, never cacheable by member-agnostic query key. Client knows `requestGeneration`, discards stale responses on account/context change, aborts fetches and clears private state before rendering a new subject. Unknown/401/403, logout, refresh failure, revoked session, session A-to-B or environment change all unmount private modules and clear drafts, preferences, pending confirmations and photo previews. Same-owner token refresh may preserve draft only after revalidation and matching boundary; it never replays writes automatically. Cross-tab signal contains only an auth-change nonce, no token or private draft. Existing `member-journey-events.mjs` and auth-change event patterns are reusable after review.

## Protected Storage and lifecycle specification

Propose a separate private `member-profile-photos` bucket only after approval. Paths use environment/owner/random object identity; policy enforces exact bucket and authenticated owner, never trusts a client path prefix alone. Upload capability is short lived and bound to owner, object key, MIME, max bytes and request identity. Finalization independently verifies actual bytes/type/dimensions and strips EXIF using an approved safe processing strategy; unsupported/corrupt/SVG/polyglot images rejected, not blindly displayed. Define bounds before implementation, proposed JPEG/PNG/WebP,5MB,4096px maximum, subject to cost/security review.

No remote image fetch; no overwrite/upsert first. Replace by new immutable object then atomic metadata switch; remove old object through an owner-bound, retryable cleanup plan. GET uses authorized short-lived signed URL or same-origin guarded bytes, no public bucket URL and no logging of signed URLs. Signed URL validity and browser cache cannot be instantly revoked: privacy change stops new grants, uses short TTL/no-store and deletes/rekeys if immediate invalidation is required; owner must approve residual-access semantics. List access cannot expose other owners. Export needs object-byte inclusion plus manifest/hash and deletion must settle pending/old/orphan objects. Existing deletion pipeline blocks owned Storage; resolve with explicit targeted lifecycle extension, not a service-role bypass in the member BFF. Storage backup/object recovery remains independent from PITR.
