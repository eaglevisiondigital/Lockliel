## Authorization and server safeguards

Reuse requireSession -> Auth user validation -> active-session RPC -> authenticated caller bearer -> RLS. Do not use service keys to make a failed owner query work. JWT AAL decoding is a presentation hint until token/session validation; staff role authorization is database-backed, active-session and AAL2, never application/tag/user_metadata input. Retain ordinary AAL1 member access only for explicitly permitted owner operations. Retain manager AAL1 denial/AAL2 permission separately from ordinary member session acceptance. No new manager role or MFA reset is approved.

Current cookies are HTTP-only/SameSite=Lax and Secure in isolated hosted mode. That alone is not a complete CSRF contract. Existing Origin checks vary and often accept missing Origin; profile/preferences/private Faith writes need a centrally reviewed mutation guard before new adapters expose them. Proposed guard checks actual allowed application origin, JSON content type/body limits, same-origin Fetch Metadata where supplied, and a server-bound unpredictable CSRF token for cookie-authenticated state changes; reject missing/foreign proof according to explicit client contract. Do not weaken CSP/CORS, accept request-host as backend identity, or trust forwarded headers. Native form/pre-hydration safety and login/logout CSRF require separate focused coverage. No Auth handlers change in this plan.

Session refresh calls rotate tokens and may conflict across concurrent requests. Serialize refresh in the browser/BFF strategy and test concurrent expiry with two tabs; never overwrite a newer session with late older cookies. Logout clears cookies/private UI even if upstream fails, reports server-revocation uncertainty rather than claiming guaranteed global logout. Sensitive server operations recheck active-session; no deleted-user JWT assumption. Account deletion revokes/checks sessions through the existing controlled operator pipeline.

## RLS, ACL and Data API gate

Readiness must inspect final effective table AND column privileges, RLS policies/role applicability, views/security_invoker, function owners/security mode/search_path/EXECUTE ACL, exposed schemas, current default ACL and actual REST/RPC access using isolated ownerA/ownerB/anon/managerAAL1/managerAAL2. A default grant is creation behavior, not proof a particular table is reachable now; RLS ON is not proof of table-level or function-level denial. Security-definer functions require bounded reason, explicit identity/session checks and no public default EXECUTE. Prefer invoker functions; private helper schema is not a client API. Never alter global default privileges or historical migration279 simply to match a new provider default.

Supabase's current [Data API security guide](https://supabase.com/docs/guides/api/securing-your-api) distinguishes grants from RLS and warns platform defaults are changing. Test current project defaults and final privileges separately; do not assume objects inherit either old or new defaults. Retained October30 exposure notice remains a release gate, not evidence it is fixed. No project Data API setting was read or changed here.

For existing lesson_private_notes, preserve exact owner/session policy and reviewed RPC plus zero effective service_role table AND column privileges. The production274 table absence is not a PASS of280 note security. New owner-private Prayer/growth/Anchor tables cannot inherit staff or service-role broad reading because their bodies are sensitive. Export/deletion privileged paths need targeted design and negative tests, not generic service SELECT.
