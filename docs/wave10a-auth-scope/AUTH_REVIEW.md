### Logout scope requires explicit treatment

Current [Supabase sign-out documentation](https://supabase.com/docs/guides/auth/signout) distinguishes default global logout from local current-session logout. The [official Auth REST specification](https://raw.githubusercontent.com/supabase/auth/master/openapi.yaml) identifies `scope` as the POST `/logout` query parameter. The existing handler does not request local scope. For this isolated acceptance package, explicitly require POST `/auth/v1/logout?scope=local`, with no global or others behavior; the confined transport must reject every other logout query. This is a proposed narrowing, not an executed provider call. Public current-source documentation is not proof of the isolated project's running Auth version.

Cookie clearing and provider revocation are separate outcomes. A future local sign-out should clear the exact host-only cookies and immediately clear the displayed member projection even when the access cookie is expired, malformed or foreign. Such rejected tokens must never be sent to the provider. With a valid isolated token, attempt only explicitly local revocation; if the provider fails, report local sign-out without falsely confirming revocation. The existing current-session RPC remains required for subsequent private reads. This does not promise immediate invalidation of a copied JWT on unrelated external clients.

### Independently reviewed exact lifecycle policy

The coordinator's concrete narrowing is acceptable for a later explicit local implementation authorization:

- A valid isolated access token may reach only POST `/auth/v1/logout?scope=local`. On provider failure, clear this host's cookies and member display, and report a generic local-sign-out result with revocation unverified. Never retry global/others or refresh automatically.
- Expired, malformed, foreign or missing access cookies trigger only exact host-local cookie clearing and view invalidation, with zero provider Auth calls. Do not assert that any remote session was revoked.
- When a new password grant indicates MFA is required, fail closed before any success-cookie response is committed to the browser. Clear any current browser state. A scoped isolated-only factory callback may retain the newly issued token in server process memory solely to attempt local revocation of that new grant. If revocation fails, report revocation unverified and stop acceptance. Do not expose the grant, manager/security routes, privileged data or MFA challenge/reset functionality. Production default MFA behavior remains unchanged.
- Cookie security must not depend on setting global environment variables. The smallest explicit isolated-only adapter reuses the existing cookie serialization/encoding, names, expiry and clearing semantics, then requires fixed allowed cookie names, Path=/, HttpOnly, SameSite=Lax, no Domain and Secure on every emitted or cleared cookie. If the existing helper omits Secure, the isolated adapter appends that attribute before any response is emitted. Any other shape mismatch fails closed. This adapter is callable only behind the existing exact HTTPS-origin/runtime guards. Both production serialization defaults and process environment remain unchanged.

These are proposed Auth lifecycle and cookie-composition behavior changes, not already implemented controls. Future tests must cover absent/contradictory environment variables, success and clearing cookies, preexisting-cookie MFA denial, local-revocation failure, and zero upstream calls for rejected cookies. Generic messages must not include provider errors, credentials, token claims or session identifiers.
