# Wave 7 owner-scoped offline read models

This is implemented offline read-model infrastructure, not live authenticated acceptance. `mode: offline-authenticated` means a trusted synthetic fixture capability was issued in memory. It does not mean a real user signed in, a Supabase session was validated or data was persisted. The ordinary member review remains a separately gated synthetic reference. Nothing is sent, saved, uploaded or activated.

## Architecture and interfaces

`contracts.ts` defines the minimal display DTO, explicit feature availability and two deliberately different ports. `MemberReadPort` is the replaceable OFFLINE actor-selection interface used by this review. Its fixture selector is never a production authentication interface. `ExistingBffSessionPort<RequestContext>` is a future server-only seam: an implementation must derive current identity from existing Netlify `requireSession`, Auth user validation and the active-session RPC, with caller bearer/RLS. No connected implementation, HTTP client, credential handling or alternate Auth system is present.

`createOfflineMemberAdapter()` issues frozen, opaque objects registered in a private per-adapter WeakMap. Copied objects, browser-supplied owner IDs, staff selection, unknown actors, unknown permission states and sessions issued by another adapter are denied. Roles and fixture response metadata do not grant permission. Invalidation increments an authority epoch. Clock expiry and epoch are checked both before and after asynchronous work. `readMember` accepts no owner ID and never falls back to another account. The optional `fixtureFor`/`wait` functions are privileged test injection seams, not browser-provided responses or transport configuration. There is no fetch or URL configuration path.

`createMemberReadController()` clears its loaded model synchronously on every load/reset, aborts outstanding work and increments generation. Session and response completion are fenced by generation and AbortSignal, including a transport that ignores cancellation. Dispose cancels and removes listeners. A component must key private local state by controller generation/boundary and clear on any account/session/context change. This is tested for A to B, anonymous, expired, denied, reset, reload and disposal. The controller also schedules automatic private snapshot clearing at the bounded fixture session expiry, validates the lifetime metadata and cancels old timers on reset, account switch and disposal. Injected clock/scheduler tests prove natural expiry without another request and ensure an old timer cannot clear a new account. A future connected adapter still needs authoritative Auth-change/revocation and cross-tab notifications before continuous live-session acceptance can be claimed.

No raw JSON crosses into a component. The adapter rejects accessor-bearing values, unexpected prototypes, cycles and oversized trees, then allowlists display fields into deeply frozen DTOs. Profile identity is checked against the runtime capability and raw session subject. Course learner identity is independently checked. Unknown or failed upstream profile/preferences cannot be displayed as verified initialized defaults. Only the explicit offline-reviewed public invitation paths /faith-boost and /getting-a-grip are allowed; arbitrary local or protected member/admin routes are denied. Unsupported catalog entries produce unavailable rather than a misleading verified empty list. Errors are generic and never echo raw service exceptions or private payloads.

The current My Five detail envelope itself has no owner field. Ownership is a server/BFF trust condition, established by the caller-bound `ownPerson` query, not by a browser comparison. This offline fixture supplier is bound to the capability's owner. A future connected transport must bind all constituent responses to the same validated session, reject generation changes and never accept a supplied arbitrary person response as trusted. This adapter does not claim cryptographic owner attestation from legacy JSON alone.

The read-model `revision` and profile/course/catalog revisions are explicit offline snapshot markers. Existing session, journey and catalog API responses do not supply equivalent aggregate CAS versions. These values are not asserted as live database revisions. Communication `updated_at` and My Five `person.version` retain existing shapes. A later connected aggregate read requires an approved trustworthy revision strategy rather than fabricating a live revision1. Unknown consent/resource revision is a release blocker for connected share preview.

## Validation and boundaries

67 focused tests cover minimal projection, all requested denial/availability states, independent A/B, forged/cloned/cross-adapter authority, role denial, expiry/revocation before and after wait, cancellation, stale revision, generic failures, accessors/cycles/oversized trees, immutable state, protected resource paths, consent denial and zero fetch calls. The ten controller and twelve presentation-guard cases are included in that total, not additive. Scoped strict TypeScript and zero-warning lint pass. Coordinator owns full application/build/browser validation and exact committed source identification.

No Supabase/API query, credentials, sessions, settings, migration, Storage, maintenance, deployment, push, merge, financial or role action occurred. Source evidence is local repository inspection only. Runtime RLS, effective ACLs, provider account state, current course binding and real CAPTCHA remain unverified by this package. All connected integration requires its own exact-source/environment/session/deployment acceptance authority.
